==================================================
A. OWNERSHIP / IDOR / BOLA
==================================================

Project invariant:

ACCESS = ROLE + OWNERSHIP + BUSINESS STATE

Audit that:
- userId/buyerId is derived from principal
- vendor/shop is derived from persisted identity
- addresses are owner scoped
- cart is owner scoped
- buyer orders are owner scoped
- vendor orders are shop scoped
- product mutations require owned shop
- governance actions require the correct Ops role
- foreign/missing resource behavior does not leak sensitive facts

Prefer scoped queries such as:
findByIdAndBuyerId / findByIdAndShopId
where appropriate.

Client-provided:
userId
buyerId
ownerId
vendorId
shopId

must never be sufficient to establish authorization.

Add regression tests for ID swapping.

==================================================
B. DTO / MASS ASSIGNMENT / TAMPERING
==================================================

Audit ALL request DTOs and form bindings.

Entity objects must not be bound directly from browser forms.

Client must not be able to control server-owned fields such as:
- role
- account status
- emailVerifiedAt
- tokenVersion
- shop approval/moderation status
- product moderation status
- ownerId
- buyerId
- vendorId
- shopId when ownership is server-derived
- price snapshot
- subtotal
- shipping fee
- grand total
- commission policy/rate/amount
- payment status
- paid amount
- order status
- inventoryReleasedAt
- lifecycle timestamps
- audit actor
- history actor
- request hash

Use DTO whitelisting.
For JSON endpoints, ensure unknown dangerous fields cannot silently become authority.

Add tampering tests.

==================================================
C. CSRF
==================================================

JWT is stored in browser cookie, therefore CSRF stays enabled.

Audit all unsafe methods:
POST
PUT
PATCH
DELETE

Requirements:
- Thymeleaf forms include CSRF.
- AJAX uses CSRF header.
- login/logout security remains coherent.
- no global csrf.disable().
- no broad ignored route such as /api/**.
- any exact server-to-server callback exemption must have a documented reason and its own signature/idempotency validation.

Regression tests must prove unsafe mutations fail without CSRF and pass with valid CSRF where the role/ownership is correct.

Do not weaken CSRF to fix tests.

==================================================
D. XSS / INPUT / QUERY HARDENING
==================================================

Audit rendered user-controlled text:
- profile/shop/product
- address
- order snapshots
- cancellation reason
- engagement
- admin/audit pages

Requirements:
- use th:text for user content
- no unsafe th:utext for untrusted content
- JS notification/text rendering must eventually use textContent, not innerHTML
- parameterized DB queries
- sort names are whitelisted
- validation has useful size/range limits

Do not add a generic sanitizer as a substitute for correct output encoding.

==================================================
E. UPLOAD SECURITY
==================================================

Audit every CURRENT file upload route, especially avatar/product images.

Verify:
- allowed extension whitelist
- MIME validation
- actual file/content validation where supported
- file size limit
- count limit
- image dimensions where current contract requires it
- generated storage key / no path traversal
- filename not trusted as filesystem path
- no executable/script content served as active content
- ownership checked before replacing/deleting an uploaded file
- invalid uploads leave no partial DB/file state
- safe deletion/replacement semantics

Do not implement future Review video upload in SEC-02.

Add malicious upload tests for realistic current upload surfaces.

==================================================
F. JWT / AUTHENTICATION HARDENING
==================================================

Audit current JWT implementation without redesigning it.

Expected contract:
- HttpOnly cookie
- Secure according to environment policy
- SameSite=Lax or existing agreed equivalent
- token expiry enforced
- persisted current account rechecked
- tokenVersion checked
- current persisted roles are authoritative
- logout/reset password/role change/account lock invalidate old JWT according to existing design
- no parallel session authentication mechanism bypassing JWT

Do not introduce refresh token tables or Redis/denylist unless the Master Plan explicitly changes.

==================================================
G. WEBSOCKET SECURITY CONTRACT
==================================================

IMPORTANT:
SEC-02 defines/hardens the SECURITY CONTRACT.
Do NOT prematurely implement WS-01/WS-02 feature scope if it does not yet exist.

Inspect current WebSocket/STOMP code, if any.

Required final contract for future/current socket implementation:
- handshake /ws authenticates from valid JWT cookie
- STOMP CONNECT requires valid CSRF token
- allowed Origin is explicit
- server establishes Principal
- client cannot choose arbitrary recipientId
- private destination:
  /user/queue/notifications
- client cannot subscribe another user's queue/topic
- client cannot publish directly into protected broker destinations
- no address/phone/payment details in notification payload
- inbound frames re-check authentication as required
- expired/revoked/locked/role-changed JWT cannot retain privileged socket access

If WS implementation is not yet present:
- document the enforceable contract
- add reusable security boundary/config only if it is required now and does not implement the future feature
- do not invent notifications, shipment events, or realtime business logic

Master requires WS-02 later to depend on SEC-02, so SEC-02 must leave a clear security contract for QD.
