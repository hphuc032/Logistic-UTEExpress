- expires_at TIMESTAMPTZ NOT NULL

Index recommended:

(user_id, purpose, sent_at DESC)

Constraints phải validate:

attempts >= 0

expires_at > sent_at

consumed_at is null
OR consumed_at >= sent_at

code_hash not blank

12. OTP HASHING
==================================================

OTP 6 chữ số có entropy thấp.

Không dùng plain:

SHA256(code)

vì database compromise có thể brute-force 1,000,000 values.

Use keyed HMAC:

HmacSHA256

với server-side secret / pepper.

Configuration:

OTP_PEPPER_BASE64

Decoded pepper:

>= 32 bytes.

Recommended input to MAC:

userId
purpose
OTP

Ví dụ canonical input concept:

<userId>:<purpose>:<code>

Store HMAC result dưới dạng:

lowercase hex 64 chars
hoặc Base64 cố định.

Nếu dùng hex:
DB code_hash length phù hợp.

Verification phải dùng constant-time comparison:

MessageDigest.isEqual(...)

Không implement custom encryption.

Không reversible-encrypt OTP.

==================================================
27. VERIFY TRANSACTION
==================================================

Verification phải transactional.

Flow:

1. normalize identifier
2. resolve user
3. only PENDING_VERIFICATION can be activated
4. load latest EMAIL_VERIFICATION OTP with locking
5. reject consumed
6. reject expired
7. reject attempts >= max
8. hash submitted code
9. constant-time compare
10. if wrong:
    increment attempts atomically
11. if correct:
    mark token consumed
    set user status ACTIVE
    set email_verified_at = server now
12. commit atomically

Token success + activation phải nằm cùng DB transaction.


==================================================
28. CONCURRENCY
==================================================

Avoid double activation / race.

Use appropriate locking.

Recommended:

PESSIMISTIC_WRITE

on latest OTP and/or relevant user row
during verification.

Two simultaneous correct submissions:

- must not corrupt attempts
- must not activate twice inconsistently
- one successful verification is enough
- second request should safely see already-completed state

Do not rely only on browser behavior.
