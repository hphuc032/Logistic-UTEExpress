### A. Authentication and JWT

Verify:

- Valid credentials authenticate correctly.
- Invalid credentials are denied.
- Passwords are stored using BCrypt.
- Pending/locked/inactive accounts cannot authenticate.
- JWT signature, issuer, audience, expiration and required claims are validated.
- JWT cookie configuration is correct for the approved HTTP/HTTPS environments.
- HttpOnly and SameSite restrictions are enforced.
- Secure is enforced where HTTPS is required.
- Logout invalidates previously issued tokens through tokenVersion.
- Password change/reset invalidates previously issued tokens.
- Role changes invalidate previously issued tokens.
- Account lock invalidates previously issued tokens.
- Roles are reloaded from persisted authority, not trusted from stale JWT claims.
- JWT is not stored in localStorage.
- Authentication is not duplicated through an independent HTTP session-login mechanism.

Use the project's existing JWT contracts as source of truth.

Avoid introducing a new refresh-token framework or MFA system.

### B. OTP security

Verify:

- Registration creates the correct pending account state.
- OTP activation requires the correct purpose.
- Reset OTP cannot be reused for activation and vice versa.
- Expired OTP is rejected.
- Already-consumed OTP is rejected.
- Incorrect OTP increments the relevant attempt counter.
- Maximum attempts are enforced.
- Resend cooldown is enforced.
- Old OTP is invalidated after resend.
- OTP consumption is atomic under concurrent requests.
- Duplicate normalized email/username registration is rejected.
- No account-existence disclosure beyond the approved response contract.
- OTP/password-reset endpoints follow configured anti-abuse limits.
- Raw OTP and its sensitive values are absent from application logs and API responses.

Master Plan reference values include five-minute expiry, maximum five attempts and resend cooldown of at least 60 seconds. Verify their actual implementation and configuration before asserting compliance.

Use deterministic Clock fixtures and PostgreSQL integration tests for race conditions.

Do not log real OTP values as evidence.

### C. RBAC and authorization

Test the six actors:

- Guest
- User
- Vendor
- Manager
- Admin
- Shipper

Use the Master Plan H1/H2 permission matrix.

Verify unauthorized access is denied at both HTTP and service boundaries where applicable.

High-priority scenarios:

- Guest cannot invoke authenticated commands.
- User cannot access Vendor management.
- Vendor cannot access another Vendor's Shop or products.
- Manager cannot assign Admin roles or lock accounts.
- Manager cannot approve/reject Shop applications where the matrix reserves that for Admin.
- Manager cannot view Admin-only global audit and account reports.
- Manager cannot access Admin financial reporting.
- Admin cannot bypass Order state machine.
- Admin cannot impersonate Buyer to create reviews.
- Shipper can only access currently assigned deliveries.
- Revoked roles immediately lose authorization according to the tokenVersion contract.
- Last active Admin protection is enforced.

Check endpoint security and direct service invocation.

Do not consider a hidden UI link equivalent to authorization.

### D. Ownership / BOLA / IDOR

Verify owner-scoped access for:

- Profile and Address
- Cart and CartItem
- Buyer Orders and returns
- Vendor Shop and Product
- Vendor Order and Dashboard
- Shipper assigned Shipment
- Review and ReviewMedia
- Notification inbox and mark-read
- Admin/Manager data scopes

Create separate authorized accounts and owned resources.

Attempt cross-account access using IDs from another actor.

Test both read and mutation behavior.

Verify rejected mutations do not alter persisted state.

Ensure userId, shopId, commissionRate, paidAmount or role sent from the browser cannot override server-derived identity or authoritative values.

Check scoped repository/service queries and DTO field whitelisting.

### E. CSRF protection

Because the application uses cookie-based JWT authentication, CSRF remains required.

Verify:

- POST/PATCH/DELETE requests without valid CSRF protection are denied.
- Thymeleaf forms include valid CSRF inputs.
- AJAX commands include the required CSRF header.
- Login/logout and state-changing operations follow the approved CSRF policy.
- Invalid or cross-session CSRF values are rejected.
- No broad `csrf.disable()` or unrestricted ignoring matcher exists.
- Any payment-provider callback exemption is narrow, justified and separately protected.

Test representative endpoints from Identity, Shop, Order, Governance and Shipping.

Verify denied requests have no unintended database side effects.

### F. Upload and file security

Inspect Avatar, ProductImage and ReviewMedia upload services.

Verify:

- Allowed JPEG/PNG/WebP formats.
- File extension validation.
- Declared MIME validation.
- Real file-content validation.
- File-size limits.
- Image-count limits.
- Dimension restrictions where specified.
- Client filenames do not become filesystem paths.
- Server-generated safe storage keys.
- No path traversal.
- No public executable SVG/HTML/script upload.
- Storage outside executable application directories.
- Ownership and role checks on upload/delete.
- Restricted access to private media where required.
- Safe handling of interrupted transactions and cleanup/reconciliation.

Master Plan proposed limits:

- Avatar: 2 MB.
- Product/Review image: 5 MB per image.
- Maximum five images per Product.
- Maximum three images per Review.

Confirm whether these are the final approved application limits before changing production settings.

Use isolated synthetic files for tests. Do not upload malicious payloads to external services.

### G. XSS, injection and output safety

Review and test:

- Thymeleaf output escaping.
- Product description rendering.
- Review comments.
- Notification rendering.
- Search and sorting parameters.
- Error responses.
- Dynamic SQL parameters.
- User-controlled image names and metadata.

Required behaviors:

- User-controlled plain text remains escaped.
- Unsafe HTML is not rendered as executable content.
- Client notification rendering uses safe text APIs.
- SQL values are parameterized.
- Sort columns are whitelisted.
- Invalid inputs do not produce stack traces or SQL errors in browser responses.
- No mass assignment of sensitive Entity fields.

Use harmless synthetic test strings and assertions.

Do not run destructive SQL against shared environments.

### H. WebSocket / STOMP security regression

Although QĐ owns Notifications, QA-01 must verify relevant cross-module authorization requirements.

Cover:

- Authenticated handshake.
- Invalid or expired JWT.
- Wrong Origin.
- Missing/invalid STOMP CSRF.
- Private destination enforcement.
- Cross-user subscription attempts.
- Unauthorized publish to broker destinations.
- Account lock after connection.
- Logout/tokenVersion revocation.
- Role revocation.
- Sensitive information exposure.
- Notifications available through authorized inbox recovery.

Verify JWT and authorization checks on inbound frames as required by the current WS-02 contract.

Preserve INT-02 transaction guarantees:

- Persist inbox inside the business transaction.
- Rollback leaves no successful notification.
- WebSocket dispatch occurs after commit.

Do not alter approved WebSocket design unless a confirmed security defect requires remediation.
