# DB-01 Database conventions

Owner: Quốc Đạt (QD). Reviewer: Tiến Đạt (TD). Source: Master Plan E1–E4,
M2–M4 and DB-01. This task establishes infrastructure and documents all 30
planned tables. It does not implement their entities or business services.

## Database and baseline

Use PostgreSQL across development, shared environments and integration tests.
The automated baseline test uses PostgreSQL 17.6. The database and login are
provisioned outside the application; Flyway creates the `uteexpress` schema
and stores `flyway_schema_history` there. Hibernate uses the same schema.
The history table is infrastructure, not one of the 30 business tables.
Run the application JVM with `-Duser.timezone=UTC`, including IDE launches.
Surefire and Failsafe set the same property. PostgreSQL may reject legacy JVM
timezone aliases (observed: `Asia/Saigon`) during connection startup, before
Hibernate's `jdbc.time_zone` applies. The integration test verifies the database
session timezone is UTC. User-facing formatting remains Asia/Ho_Chi_Minh.

`V20260920143000__qd_db01_schema_baseline.sql` records a schema comment only.
There are deliberately no business tables yet. This is an ordinary versioned
migration, not Flyway's baseline command. Do not enable baseline-on-migrate
to hide an existing schema. An existing populated database needs a separately
reviewed adoption plan. Boot fails if connection or migration validation fails.

Flyway is the schema writer; Hibernate uses `ddl-auto=validate`. No `update`,
`create`, `create-drop`, SQL init scripts or H2 substitutions. Open Session in
View is disabled. Keep clean disabled and out-of-order disabled.

## Columns and mappings

| Concern | Convention |
| --- | --- |
| Names | Unquoted lowercase snake_case; table names follow E2 exactly |
| Primary key | `id BIGINT GENERATED BY DEFAULT AS IDENTITY`, Java `Long` |
| Exception | `user_roles` has composite PK `(user_id, role_id)`, no extra id |
| Foreign keys | `BIGINT`, explicit constraint `fk_<table>_<column>` |
| Mutable records | `created_at` and `updated_at` as `TIMESTAMPTZ NOT NULL` |
| Timestamps | Java `Instant`, UTC; UI displays Asia/Ho_Chi_Minh |
| Audit timestamps | Creation default `CURRENT_TIMESTAMP`; owner updates `updated_at` on every write, including bulk SQL; a default is not an update trigger |
| History | Append-only `created_at`; preserve E2 event times such as `requested_at` and `last_viewed_at` |
| Money | `NUMERIC(19,2)` / `BigDecimal`; never float/double |
| Percentages | Decimal with CHECK 0–100; precision agreed with pricing owner TD |
| Enums | `VARCHAR` + named CHECK; JPA `EnumType.STRING`; never ordinal/native PostgreSQL enum |
| Concurrency | `version BIGINT NOT NULL DEFAULT 0` / `@Version Long` on E2 versioned entities |
| Indexes | `ix_<table>_<columns>`; unique `uq_<table>_<columns>`; checks `ck_<table>_<rule>` |

Do not invent enum members here. Identity/security enums belong to HP,
Order/Payment states to TD, Shipment states to QD. Expand checks with a new
migration after owner agreement. VND rounding stage and mode must follow the
ORD-00 pricing contract; DB-01 specifies storage only.

## Required constraints from E4

- Normalize email/username consistently before storage and enforce uniqueness.
- Unique role code, shop owner, cart user, cart/product, favorite user/product,
  product-view user/product, order code and `(buyer_id, checkout_key)`.
- Unique shipment/order, review/order item, voucher usage/order, return/order,
  refund/order, payment attempt key and nullable provider reference.
- Partial unique address index on `user_id WHERE is_default = true`; service
  still guarantees at least one default when a user has addresses.
- One successful payment per order: partial unique index with the exact success
  state supplied by TD. Do not prematurely invent a PaymentStatus literal.
- `price > 0`, `stock >= 0`, `quantity >= 1`, rating 1–5, nonnegative money,
  bounded percentages and `starts_at < ends_at`. Add NOT NULL where mandatory;
  SQL CHECK alone does not reject NULL.
- Product(category_id, status), Product(shop_id, status),
  Order(buyer_id, created_at), Order(shop_id, status),
  Shipment(assigned_shipper_id, status), Notification(recipient_id, read_at).
- Do not cascade delete order/payment history with users or products.
  Product/shop/category/provider use state changes when referenced.
- OrderItem and address/pricing snapshots preserve checkout facts. Do not
  replace snapshots with live product/address values.
- `audit_logs.target_id` is a logical reference, never a polymorphic FK.

E3 describes at most one refund per payment/return request. TD must carry those
cardinalities into the later migration (unique nullable FK as appropriate),
and validate that the refund/payment/return all belong to the same order.
This records the existing ERD requirement; no ERD change is introduced here.

## Migration workflow

Use `VyyyyMMddHHmmss__<owner>_<task>_<description>.sql`, UTC, e.g.
`V20260921101530__hp_auth01_identity.sql`. Seconds prevent most collisions;
QD still checks uniqueness and dependency order before every merge.

1. Start a task branch from updated develop. Read the ordering manifest.
2. Each owner writes their own tables and constraints, prerequisite tables first.
3. Compare the timestamp with all migrations already merged to develop. A new
   migration must sort after their maximum version and its prerequisites.
4. Never edit or rename a migration already merged or run on a shared database.
   Correct it with a new migration. Do not repair checksums to suppress drift.
5. If an unmerged branch has an older timestamp, coordinate with QD and rename
   only its private migration before first shared use. Recreate disposable
   local databases as needed; never apply that reset to a shared database.
6. Run fresh-database migration, validation, second migration (no pending work),
   and feature-specific FK/unique/check/transaction tests. Review by owner + QD.

See [schema and ordering](DATABASE_SCHEMA.md) and [seed manifest](SEED_MANIFEST.md).
Do not create all 30 tables in DB-01 or move module ownership to QD.

## Local and shared configuration

Set `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` in the current shell or IDE.
`.env.example` lists placeholders; Spring Boot does not load `.env` by itself.
Never commit a real credential. Local/prod profiles inherit mandatory ENV
credentials from the common configuration. PostgreSQL URL options for remote
TLS depend on the deployed provider; do not disable certificate validation.

Use a dedicated database login, not the PostgreSQL superuser. It needs schema
creation for first boot and DDL privileges for Flyway. Restrict access to the
application database. A separately provisioned migration/runtime role can be
introduced during deployment review without embedding credentials in code.

## Verification boundary

`mvnw.cmd test` and `mvnw.cmd package` run existing HTTP/architecture tests.
The test-only `application-test.yml` explicitly excludes persistence for the
foundation HTTP fixture. It is not packaged as application configuration.

`mvnw.cmd -Ppostgres-it verify` additionally boots the real application against
a fresh Testcontainers PostgreSQL database, validates the baseline and reruns
Flyway. Docker is required: missing Docker fails this command, not skips it.
The integration test uses the production database configuration with dynamic
container connection details; it does not activate the HTTP test profile.

FK/unique/check/locking tests for business tables belong to their later tasks.
Passing this schema-only baseline does not prove all of T48 or the full DoD.
