## Accepted revised protocol

- Persisted ACTIVE ADMIN eligibility under Account FOR SHARE, then fresh persisted ADMIN membership read at READ_COMMITTED, held through commit. Current governance role writers lock the target Account before membership changes; refund must not acquire Role or scope locks after Account. Same actor with extra VENDOR/SHIPPER roles gains no bypass. HP must explicitly confirm that persisted ACTIVE ADMIN is the complete current scope, not a placeholder for an unimplemented scope table.
- Global operation namespace PAY02_MANUAL_COD_REFUND_V1; UNIQUE(operation,idempotency_key) plus immutable canonical SHA-256 request hash and committed result.
- Fresh public transaction, reject any outer transaction before key lock; no REQUIRES_NEW to hide a caller-held Account/Order lock. Internal hooks MANDATORY. Explicit READ_COMMITTED, same connection/transaction for advisory lock, row locks and inserts.
- Transaction key lock -> Order -> ReturnRequest -> Payment -> existing Refund if any -> ADMIN Account -> inserts/effects. Existing Refund reads do not move an insertion ahead of eligibility locking. All FK-related parents are already locked before ledger/idempotency/audit/history insertion; processed_by is server-derived and Account locked before its FK check. Payment locks use stable ID order and all relevant entities are refreshed.
- Only Payment-owned persisted evidence can authorize a one-shot SUCCEEDED refund; Order lifecycle alone performs RETURNED -> REFUNDED, history and event after commit. Historical Payment PAID, ReturnRequest APPROVED/receipt/version and Shipping/Inventory/Voucher facts stay unchanged. Retain full atomic rollback.

## Advisory-key protocol that must be preserved in implementation

Use transaction-scoped pg_advisory_xact_lock, not session-scoped pg_advisory_lock. It is released at transaction end (PostgreSQL 17 explicit-locking documentation). Derive a stable lock identity from operation + canonical idempotency key ONLY; exclude actor, Order and payload hash. Otherwise same global key on different Orders/actors/payloads would take different locks and bypass the intended collision serialization. Specify deterministic encoding/byte order if hashing to bigint; a truncated hash collision may serialize unrelated requests but must never count as idempotency equality. Full operation/key/hash equality and DB uniqueness remain authoritative.

Every PAY-02 writer acquires at most one advisory key lock before any Order/Account lock and never acquires another key lock while holding domain locks. Never perform a role-check helper that locks Account before this phase; plain request identity extraction and nonlocking validation are allowed. Existing Order flows need not take this key lock, but must never call refund while retaining an Order lock (outer transaction rejection enforces that). Bounded wait/transaction timeout; no tight application spin or unbounded retries.

After waiting for the key lock, database reads must see newly committed rows: READ_COMMITTED with lock/refresh and no cached pre-lock ledger lookup. Same-key/cross-Order collisions must not load/lock the winning DIFFERENT Order while holding the requested Order. Authorize the current actor without disclosing foreign committed results; compare stored operation, actor, Order and full canonical hash, returning generic CONFLICT for mismatch.

Same-key/same-payload committed replay is authorized before first-execution stale/state guards, returning the immutable committed result even after Order version/status changed. Original expected Order/Return versions remain in canonical payload. A revoked/inactive actor cannot replay merely because the previous result exists. Different key for the same Order serializes on Order and then conflicts through persisted successful ledger/UNIQUE(order_id). Do not turn advisory hash equality into a replay match.

Database UNIQUE constraints remain mandatory even with advisory coordination. Any unexpected uniqueness error must roll back or follow an explicit savepoint/fresh-retry protocol; no further query in an aborted transaction. Failed work must not retain a key/result/ledger or publish events. PostgreSQL advisory locks are application-cooperative, so all production mutation entry points must share the protocol.

## Schema and the two remaining DTO details

PASS on UNIQUE(order_id), UNIQUE(payment_id), UNIQUE(return_request_id), UNIQUE(operation,idempotency_key), required nonnull links, composite Payment/ReturnRequest+Order FKs to matching unique targets, server actor/time/proof and immutable one-shot SUCCEEDED ledger. Preserve UPDATE/DELETE protection and no cascade financial deletion. Local CHECKs cannot replace locked cross-table paid/receipt/entitlement verification.

Amount: CHECK(amount > 0) AND NOT NULL, fixed decimal compatible with Payment/Order. Zero-value and legacy/missing evidence fail closed as TD reports HP requires. Authority also validates refundAmount against approved positive persisted grand_total and successful COD PAID evidence, not only the SQL CHECK. This is a design review of the reported approved formula, not a new QD policy approval; HP final contract should explicitly record shipping-fee inclusion to supersede the old goods-only wording.

paymentId: prefer omission if only one qualifying persisted COD record is allowed. If retained, it is an expected identifier only: authority independently selects/locks/verifies Payment belongs to this Order and is the eligible collected payment, then compares ID. Reject mismatches, invalid/nonpositive IDs and ambiguous evidence. Include the supplied expected paymentId (or its defined absence) in the canonical hash; never ignore its change on replay. It is not an instruction to refund an arbitrary caller-selected payment or a substitute for expected versions.

Canonicalization must define bounded key/proof text normalization, field ordering/encoding and a schema version. Actor is server-derived. No amount/status/scope/linked receipt identity is browser authoritative. Key is global within operation; committed response never leaks across actors. Routes and DTO names remain subject to HP final interface approval, including any deviation from Master routes.
